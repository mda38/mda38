# 単体テストの考え方を掴む

## この記事で書きたいこと（メモ）

- なぜ単体テストを書くのか
- 「単体」のスコープ（何を隔離する？）
- 良いテストの条件（読みやすい／壊れにくい／意図が伝わる）
- テストしやすい設計（依存注入・純粋関数・境界）
- ありがちな失敗（実装依存・過剰なモック・脆いE2E風ユニット）

## キーワード

- Arrange-Act-Assert（AAA）
- Given-When-Then
- テストダブル（Stub / Mock / Spy）
- 境界（I/O、時間、乱数、HTTP、DB）
- リファクタリング耐性

## 例にしたい題材（候補）

- 料金計算（税・割引・端数処理）
- バリデーション（入力チェック）
- リポジトリ層の境界（DBはモック／インメモリ）
