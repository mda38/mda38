# UXロジックの取り扱い

めちゃくちゃいい整理なので、構造として一段きれいにまとめます。

## 🎯 UXロジックとは何か

**UXロジック = ユーザーの行動空間を制御するもの**

* 業務ロジック → システムの状態空間を守る
* UXロジック → ユーザーの行動空間を整える

守っている対象が違う。

## 🧩 不要な操作の2分類

### ① 無駄系（Non-destructive）

例：

* 二重クリック
* 検索連打
* ページング高速連打

特徴：

* データは壊れない
* エラーにはならない
* でも体験や負荷が悪化

👉 UX最適化の領域
👉 ビジネス文脈依存（BtoCなら重要、社内画面なら低め）

### ② 破壊系（Destructive）

例：

* 空フォーム送信
* 不正値送信
* 権限なし操作
* 在庫0購入

特徴：

* バックエンドエラー
* データ不整合リスク
* ユーザー混乱

👉 事故防止UX
👉 テスト優先度は高い

## 🧠 UXロジックの3段階

1. **行動抑制**（disable / debounce）
2. **行動誘導**（デフォルト値 / フォーカス）
3. **行動補助**（オートコンプリート / 補完）

テスト価値が高いのは：

> 行動抑制 × 破壊リスクあり

## 🧪 テスト戦略の整理

### ✅ 単体テストで守る

* バリデーション判定（true / false）
* 入力 → 結果が明確な純粋ロジック

```ts
isValidEmail("") → false
```

ここは厚く守る価値がある。

### ✅ UI統合テストで守る

* エラーが表示されること
* 送信できないこと

「存在確認」で十分。

### ❌ 基本やらない

* エラーメッセージの完全一致テスト

理由：

* 文言は揺れやすい
* UX改善で変わる
* POレビューで変わる

例外：

* 法的表示
* 金融系警告
* 監査対象文言

## 🎯 本質的な設計視点

テストとは：

```
ロジックを守る
振る舞いを守る
体験の細部は守りすぎない
```

全部守ろうとすると壊れる。

守るべきは「リスク」。

## 🏗 そして最後の設計問い

UXロジックはどこに置くべきか？

* 純粋判定 → ViewModel / domain寄り
* 表示制御 → UIコンポーネント
* 複数フィールド横断 → フォームレイヤー

ここが整理できると設計が安定する。
