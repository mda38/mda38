# INPUT_METADATA

theme: フロントエンドテストを「書き方」ではなく「設計」から捉え直す
target: フロントエンドテストに迷いを感じている初学者〜中級者、AIでテストコードを生成しているが設計に自信がない開発者
intent: テストに対する「何を・なぜ・どのレイヤーで」書くべきかという判断基準を整理し、再利用可能な思考フレームとして提示する

---

# RAW_CONTEXT（スレッド要約）

このスレッド全体では、フロントエンドテストを単なる実装手法としてではなく、設計対象として整理し直そうとしていた。出発点は「AIでテストコードは生成できるのに、良いテストを書いている感覚がない」という違和感だった。そこから、問題はテストコードの書き方ではなく、テスト対象の把握・テスト価値の判断・レイヤーごとの役割分担が曖昧なことにあると整理された。

議論の中では、フロントエンドの責務を UI / ユーザー操作 / 判断ロジック / 外部依存 に分解し、特に「判断があるところにテスト価値がある」という軸が見えてきた。また、Unit / Integration / E2E という分類も名前で覚えるのではなく、「どの責務をどのレイヤーで最も素直に検証できるか」という戦略として再定義された。さらに、AIは実装補助には強いが、何をテストすべきかという設計判断は人間側の仕事である、という結論に至った。

そのうえで、記事として読まれる形にするために、タイトル・導入・具体例まで含めて、読者のもやもやから入り、考え方の整理に導く構成へと磨き込む方向が確認された。

---

# PROBLEM（問題提起素材）

* テストコードは書いているが、何を守れているのか自分でもよくわからない
* AIでテストコードは生成できるが、そのテストに価値があるか判断できない
* Unit / Integration / E2E の名前は知っていても、どこに何を書くべきか整理できていない

---

# INSIGHTS（重要な気づき）

* テストの問題は「書き方」の不足ではなく、「何をなぜテストするか」という設計不足で起こる
* フロントエンドテストの価値は、表示そのものよりも、表示や操作の背後にある判断ロジックに宿りやすい
* AIはテストコードの生成には役立つが、テスト対象の選定やレイヤー分配といった設計判断は代替しにくい

---

# STRUCTURE（構造）

## テスト対象の分解

* フロントエンドは UI だけでなく、操作・判断・外部依存を含む複合的な責務を持つ
* テストは画面全体を漠然と捉えるのではなく、責務単位に分解して考える必要がある
* まず「何が起きているか」ではなく「どんな責務がそこにあるか」を見る

## テスト価値の判断

* すべてをテストするのではなく、壊れたら困る・複雑・変更されやすい箇所を優先する
* 特に条件分岐・変換・制御のような判断がある箇所はテスト価値が高い
* 単純表示やライブラリ依存の挙動は、相対的にテスト価値が低くなりやすい

## テスト戦略の整理

* Unit / Integration / E2E は知識ではなく、責務を置く場所として理解する
* 判断ロジックは Unit、UI とロジックの接続は Integration、ユーザーフローは E2E が向いている
* 重要なのは分類名ではなく、「最も自然に壊れ方を検知できるレイヤーはどこか」という視点

---

# LOGIC（本質ロジック）

* テストが難しく感じられるのは、コードを対象にしているつもりで、実際には責務や判断構造を見ずに表面だけを追っているから
* フロントエンドの多くの不具合は「表示が崩れた」ことより、「どういう条件で何を出すか」「どういう操作を許すか」という判断のズレから起きる
* だからテストは、出力そのものを広く覆うのではなく、仕様上の判断が埋め込まれている箇所を中心に配置すると、少ない本数でも価値が高くなる

---

# THINKING_FLOW（思考の流れ）

* 初期：AIでテストコードは書けるのに、何をどこまでテストすべきか分からず、良いテストを書いている実感が持てない
* 途中：問題はテスト手法の不足ではなく、フロントエンドの責務分解とテスト価値の判断軸が曖昧なことだと気づく
* 最終：フロントエンドテストは「対象を分解し、価値を判断し、適切なレイヤーに置く」という設計問題であり、AIはその実装を補助する存在だと整理される

---

# EXAMPLES（具体例）

* `user.role === "admin"` のときだけ管理者ボタンを表示する処理は、UI表示ではなく「権限判断」にテスト価値がある
* `status === "active" ? "有効" : "停止中"` のような ViewModel 変換は、単純変換に見えて仕様判断を含むため Unit テストの価値が高い
* ログイン後に管理画面へ遷移し、必要なボタンが見えるかを確認する流れは、個別ロジックではなくユーザーフローとして E2E が適している

---

# DECISION_RULES（判断基準）

* そのコードに条件分岐や仕様判断が含まれているなら、テスト価値は高い
* その責務を最もシンプルに検証できるレイヤーがあるなら、まずそこでテストする
* AIにテスト生成を頼む前に、「何を守りたいのか」を自分の言葉で説明できないなら、まだ設計が足りていない

---

# APPLICATION（応用）

* 実務での使い方：新しい画面や機能を作るとき、まず UI / 操作 / 判断 / 外部依存 に分解してからテスト対象を決める
* 設計への落とし込み：判断ロジックを ViewModel や関数に切り出し、Unit で検証しやすい形にしてから UI に接続する
* 他領域への転用：テスト以外でも、バリデーション設計・状態管理・UX制御などを「判断がどこにあるか」で分解すると整理しやすい

---

# HOOK（導入用素材）

* テストコードは書けるのに、「これでいい」と思えないことはないでしょうか
* 問題はテストの書き方ではなく、何をなぜテストするかが曖昧なことかもしれません
* Unit / Integration / E2E を知っていても、テスト設計ができるようになるわけではない
