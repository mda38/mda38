# INPUT_METADATA

theme: フロントエンドテストを「技法」ではなく「守るべきもの」から再定義する
target: フロントエンドエンジニア、テスト方針に迷っている実装者、テックリード候補
intent: フロントエンドで何にテスト価値があるのかを構造的に整理し、単体テスト・E2E・UXロジックの扱いを一貫した判断基準で決められるようにする

---

# RAW_CONTEXT（スレッド要約）

スレッド全体では、フロントエンドテストを「どの技法を使うか」から考えるのではなく、「フロントエンドの責務は何で、その責務のどこにテスト価値が生まれるか」から整理し直している。出発点は、フロントの責務を UI の表示と操作と捉え、そのために必要な判断ロジックに単体テスト価値があるのではないか、という問題意識である。そこから、フロントでテスト価値が生まれる瞬間を分岐・条件・変換・例外処理・表示/非表示・有効/無効として整理し、表示や操作そのものはロジックの結果として統合的に確認すべきだという方向に進んでいく。さらに議論は UX ロジックの扱いへ進み、UX を一律に扱うのではなく、事故防止UX・体験品質UX・装飾UXに分けて、壊れたときの損失や気づきにくさでテスト濃度を決める、という判断軸に到達している。最終的には、フロントエンドテストとは UI を直接守るものではなく、UI を成立させるための判断・変換・制御を守るものだ、という構造に整理されている。

---

# PROBLEM（問題提起素材）

- フロントエンドでは何を単体テストし、何を E2E に回すべきかが曖昧になりやすい
- UI や UX に関わる処理が「見た目の問題」として扱われ、どこに本当にテスト価値があるのか判断しづらい
- テストを書くこと自体が目的化し、壊れたときの損失や重要導線との関係が薄いまま、テストの濃淡を決められない

---

# INSIGHTS（重要な気づき）

- フロントエンドで守るべきなのは UI の見た目そのものではなく、UI を成立させる判断・変換・制御である
- UX ロジックは一律にテストするものではなく、壊れたときの被害の大きさで優先度を変えるべきである
- テスト戦略は技法中心ではなく、「誰がどれだけ困るか」を基準にすると一貫した設計になる

---

# STRUCTURE（構造）

## フロントエンドの責務

- UI を表示する
- ユーザー操作を受け付ける
- 表示や操作を成立させるために判断を行う

## テスト価値が生まれる場所

- 条件分岐や表示可否の判断
- データ変換や UI 向け加工
- 例外処理や操作制御

## テスト濃度の決め方

- 事故防止UXは高価値として厚く守る
- 体験品質UXは必要に応じて守る
- 装飾UXは基本的に厚く守らない

---

# LOGIC（本質ロジック）

- フロントエンドテストの本質は、見た目を固定することではなく、見た目や操作を決めている判断構造を守ることにある
- UI は最終表現にすぎず、その裏には「誰に何を見せるか」「今その操作を許すか」「受け取ったデータをどう意味づけるか」という解釈レイヤーが存在する
- したがって、テスト価値はコンポーネントの外形ではなく、誤表示・誤操作・誤誘導を生む分岐や変換に発生する。また UX ロジックも見た目の問題ではなく、ユーザー損失をどこで未然に防ぐかという制御の問題として理解すると、テストの優先度を合理的に決められる

---

# THINKING_FLOW（思考の流れ）

- 初期：フロントエンドでは何にテスト価値があるのか、単体テストと統合的な確認をどう分けるべきかを整理したい
- 途中：フロントの責務を UI 表示と操作と捉え直し、テスト価値はそのための判断・変換・制御にあると見えてきた。さらに UX ロジックも同じ軸で見直せることに気づいた
- 最終：フロントエンドテストは UI を直接守るものではなく、UI を成立させる判断構造を守るものであり、UX の扱いも壊れたときの損失・気づきにくさ・修正コストで濃淡をつけるべきだと整理された

---

# EXAMPLES（具体例）

- 管理者であれば管理者専用メニューを表示する。この場合、表示そのものより「管理者かどうか判断するロジック」に単体テスト価値がある
- 空フォーム送信防止や二重送信防止は UX ロジックだが、壊れると制約違反や不要な API 負荷につながるため、高価値なテスト対象になる
- ソート順が昇順か降順かは UX に関わるが、壊れてもすぐ気づけて修正も容易なため、事故防止UXほどのテスト価値はない

---

# DECISION_RULES（判断基準）

- その処理は UI の見た目ではなく、表示・操作・状態を決める判断や変換になっているか
- 壊れたときにユーザー体験だけでなく、制約違反・業務影響・誤操作などの損失が生じるか
- その不具合は気づきにくいか、影響範囲が広いか、修正コストが高いか

---

# APPLICATION（応用）

- 実務での使い方：画面ごとに「分岐・条件・変換・例外処理・表示制御・操作制御」を洗い出し、どこに単体テスト価値があるかを先に判断する
- 設計への落とし込み：単体テストは判断・変換ロジック、E2E は重要導線、軽微な装飾UXは手動確認に寄せる、という責務分担に落とし込める
- 他領域への転用：バックエンド設計やレビューでも同様に、「全部を均等に守る」のではなく「壊れたときの損失が大きく、気づきにくいものを優先して守る」という原則として使える

---

# HOOK（導入用素材）

- 読者に刺さる問い：フロントエンドのテストで、あなたは本当に「守るべきもの」を守れていますか？
- 違和感を生む一文：UI をテストしているつもりで、実は見た目しか見ていないことは多い
- よくある誤解：フロントエンドテストはコンポーネントを render して確認することだ、という理解だけでは不十分
