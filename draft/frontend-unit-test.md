## テスト対象を整理

フロントエンドの責務は主に次の2つ。

- UIの表示
- ユーザー操作の受付

そのため、UIを表示・操作するための判断ロジックがフロントには存在する。

```
例：管理者なら管理者メニューを表示する
```

このような UIの表示を決める判断 にはテスト価値がある。

そもそもフロントはバックエンドのようなドメインロジックを直接持つことは少ない。

そのためテスト対象は主に次になる。

UIに関する判断ロジック

- 分岐
- 条件
- データ変換
- 例外処理
- 表示 / 非表示
- 有効 / 無効

これらは 単体テストで保証する。

## ユーザー操作のテストは少し注意

操作後にAPIリクエストが正常に行われたかどうかや状態が更新されたかどうかなどはテストすることにあまり価値はない。
なぜなら、裏側のデータが更新されてもユーザーはそのデータを直接見ることはないからだ。

大事なのは、ユーザーから見ることができるものをテストすること。
つまり、操作とUI表示を連携させた結果をテストするようにする。

こうすることでユーザーに提供するUIの部分をテストすることができるようになる。
